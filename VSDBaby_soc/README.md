##  Objective

The aim of this experiment was to study the structure and simulation flow of the **VSDBabySoC** and understand how an RTL design behaves before and after synthesis.

The experiment focused on:

* Understanding the VSDBabySoC architecture
* Studying the RVMYTH RISC-V processor
* Understanding the role of AVSDPLL and AVSDDAC
* Running pre-synthesis RTL simulation
* Synthesizing the RTL design
* Generating and simulating the gate-level netlist
* Performing Gate-Level Simulation (GLS)
* Viewing simulation waveforms with GTKWave
* Comparing RTL and synthesized-design behavior

# 1. VSDBabySoC Overview

VSDBabySoC is a compact System-on-Chip that combines digital processing with analog interface blocks.

The major components included in the design are:

* **RVMYTH** – RISC-V based processor core
* **AVSDPLL** – Clock generation and Phase Locked Loop block
* **AVSDDAC** – Digital-to-Analog Converter

These blocks are integrated through the top-level **`vsdbabysoc`** module.

The simulation and verification process follows the sequence:

```text
RTL Design
     ↓
RTL Simulation
     ↓
Synthesis
     ↓
Gate-Level Netlist
     ↓
Gate-Level Simulation
     ↓
Waveform Verification
```

This flow helps verify the design functionality both before and after technology mapping.

# 2. VSDBabySoC Architecture

The VSDBabySoC combines the processor, clock-generation block, and DAC into a single design.

A simplified representation is:

```text
                 ┌───────────────┐
                 │    AVSDPLL    │
                 │      PLL      │
                 └───────┬───────┘
                         │
                      Clock
                         │
                         ▼
                 ┌───────────────┐
                 │    RVMYTH     │
                 │  RISC-V Core  │
                 └───────┬───────┘
                         │
                    Digital Data
                         │
                         ▼
                 ┌───────────────┐
                 │    AVSDDAC    │
                 │      DAC      │
                 └───────┬───────┘
                         │
                         ▼
                        OUT
```

The **AVSDPLL** provides the required clock signal to the processor. RVMYTH performs the digital processing, and its generated data is passed to the **AVSDDAC** for output generation.

# 3. RVMYTH RISC-V Processor

**RVMYTH** is the RISC-V based processor used in the VSDBabySoC design.

It serves as the primary digital computation unit. The processor operates using the clock supplied by the PLL and performs the programmed digital operations.

The resulting digital information is transferred toward the DAC section.

Important RVMYTH-related files include:

```text
rvmyth.v
rvmyth_gen.v
rvmyth.tlv
```

A simplified representation is:

```text
                 ┌────────────────────┐
                 │       RVMYTH       │
                 │                    │
Clock ──────────►│    RISC-V Core     │
                 │                    │
                 │ Digital Processing │
                 └─────────┬──────────┘
                           │
                      Digital Data
                           │
                           ▼
                        AVSDDAC
```

Thus, RVMYTH forms the main digital processing section of the SoC.

---

# 4. AVSDPLL

**AVSDPLL** is the Phase Locked Loop block used within the VSDBabySoC.

Its primary role is to provide the clock required by the digital processing section. The clock generated by the PLL is connected to the RVMYTH processor.

The main source file associated with this block is:

```text
avsdpll.v
```

The basic signal flow is:

```text
Input Clock
     │
     ▼
┌───────────────┐
│    AVSDPLL    │
│      PLL      │
└───────┬───────┘
        │
   Generated Clock
        │
        ▼
      RVMYTH
```

The PLL therefore acts as an important timing source for the digital portion of the SoC.

---

# 5. AVSDDAC

**AVSDDAC** represents the Digital-to-Analog Converter section of the VSDBabySoC.

It accepts the digital information generated by the RVMYTH processor and produces the corresponding output signal.

The main DAC source file is:

```text
avsddac.v
```

The simplified operation is:

```text
Digital Data
     │
     ▼
┌───────────────┐
│    AVSDDAC    │
│      DAC      │
└───────┬───────┘
        │
        ▼
       OUT
```

The DAC provides the interface between the digital processing section and the final output.

# 6. Pre-Synthesis Simulation

Pre-synthesis simulation is carried out using the original RTL description of the design.

The main purpose is to confirm that the design operates correctly at the functional RTL level before converting it into hardware gates.

## 6.1 RTL Source Files

The important files used during RTL simulation include:

```text
testbench.v
vsdbabysoc.v
rvmyth.v
rvmyth_gen.v
rvmyth.tlv
avsdpll.v
avsddac.v
clk_gate.v
```

Additional header and supporting files required by the design are included during compilation.

---

## 6.2 Compiling the RTL

The RTL sources can be compiled using **Icarus Verilog**.

First, move to the simulation module directory:

```bash
cd ~/baby_soc/BabySoC_Simulation/src/module
```

The pre-synthesis simulation can then be compiled using:

```bash
iverilog -o ./pre_synth_sim.out \
-DPRE_SYNTH_SIM \
testbench.v \
-I ../include \
-I .
```

This command creates the simulation executable:

```text
pre_synth_sim.out
```

---

## 6.3 Executing the Simulation

Run the compiled simulation using:

```bash
vvp ./pre_synth_sim.out
```

During execution, the testbench generates a Value Change Dump file:

```text
pre_synth_sim.vcd
```

This VCD file contains the signal transitions recorded during the RTL simulation.

---

## 6.4 Viewing the RTL Waveform

The generated waveform can be opened in **GTKWave** using:

```bash
gtkwave pre_synth_sim.vcd
```

The waveform can be examined to understand signal transitions and verify the functional operation of the SoC.

Signals such as:

* Clock
* Reset
* Processor-related signals
* Output signals

can be selected and analyzed in GTKWave.

# 7. Post-Synthesis Simulation

Once the RTL design has been synthesized, the resulting gate-level representation can be simulated.

This stage is commonly called **Gate-Level Simulation (GLS)** or post-synthesis simulation.

The purpose is to check whether the synthesized implementation continues to provide the expected functionality of the original RTL design.

---

## 7.1 Gate-Level Netlist

During synthesis, the RTL description is transformed into a network of logic cells.

For the target technology, the design is mapped to cells from the **SKY130 standard-cell library**.

The resulting gate-level netlist represents the synthesized hardware and becomes the input for post-synthesis simulation.

---

## 7.2 Running Gate-Level Simulation

The synthesized netlist is simulated using **Icarus Verilog**, along with the required technology-library models and supporting files.

The simulation produces a VCD waveform file:

```text
post_synth_sim.vcd
```

This waveform represents the behavior of the synthesized gate-level implementation.

---

## 7.3 Viewing the GLS Waveform

The post-synthesis waveform can be opened with:

```bash
gtkwave post_synth_sim.vcd
```

GTKWave can then be used to inspect the clock, reset, internal signals, and output behavior of the synthesized design.

The observed results can be compared with the pre-synthesis waveform to identify any functional or timing differences.

---

# 8. RTL vs Gate-Level Comparison

The two simulation stages represent different levels of the same hardware design.

| Parameter          | Pre-Synthesis              | Post-Synthesis                       |
| ------------------ | -------------------------- | ------------------------------------ |
| Representation     | RTL code                   | Gate-level netlist                   |
| Design stage       | Before synthesis           | After synthesis                      |
| Main purpose       | Functional verification    | Hardware implementation verification |
| Simulation type    | RTL simulation             | Gate-Level Simulation                |
| Technology mapping | Not yet applied            | Applied                              |
| Technology library | Not required for RTL logic | SKY130 cell models used              |
| Output waveform    | `pre_synth_sim.vcd`        | `post_synth_sim.vcd`                 |
| Waveform tool      | GTKWave                    | GTKWave                              |

The overall verification process can be summarized as:

```text
RTL Source
    ↓
Pre-Synthesis Simulation
    ↓
RTL Waveform
    ↓
Synthesis
    ↓
Gate-Level Netlist
    ↓
Post-Synthesis Simulation
    ↓
GLS Waveform
    ↓
Comparison
    ↓
Functional Verification
```

The comparison helps determine whether synthesis has preserved the intended logical behavior.

# 10. Conclusion

The VSDBabySoC design was examined through both **pre-synthesis RTL simulation** and **post-synthesis Gate-Level Simulation**.

The experiment provided an understanding of the interaction between the major blocks: **RVMYTH**, **AVSDPLL**, and **AVSDDAC**. RVMYTH performs the digital processing, AVSDPLL supplies the required clock, and AVSDDAC handles the digital output interface.

Initially, the RTL design was compiled and simulated using Icarus Verilog. The generated `pre_synth_sim.vcd` waveform was then inspected with GTKWave.

After synthesis, the technology-mapped gate-level netlist was simulated to generate the post-synthesis waveform. Comparing the RTL and GLS waveforms helps confirm that the synthesized hardware retains the intended functional behavior.

The complete process can be summarized as:

```text
VSDBabySoC RTL
      ↓
RTL Simulation
      ↓
Pre-Synthesis Waveform
      ↓
Synthesis
      ↓
Technology-Mapped Netlist
      ↓
Gate-Level Simulation
      ↓
Post-Synthesis Waveform
      ↓
Waveform Comparison
      ↓
Design Verification
```

Overall, this experiment provided practical exposure to **SoC architecture, RISC-V processor integration, PLL and DAC blocks, RTL simulation, synthesis, Gate-Level Simulation, and waveform-based verification using GTKWave**.
